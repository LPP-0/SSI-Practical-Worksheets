# Semana 6 - Cifras Modernas

## Questão 1

Usar um **NONCE fixo** é uma falha de segurança catastrófica que destrói completamente a confidencialidade da cifra. A segurança de uma cifra de fluxo como a *ChaCha20* depende da unicidade do par (chave, NONCE).

O NONCE numa cifra sequencial como *ChaCha20* é utilizado para garantir que o *keystream* gerado pela cifra é diferente em cada operação de cifragem, mesmo quando a mesma chave é utilizada.

Se a chave (K) e o NONCE (N) forem os mesmos para duas mensagens diferentes (P1 e P2), o keystream gerado será idêntico. Isto leva ao mesmo ataque de reutilização de chave que vimos na *One-Time Pad*, na ficha da semana 5.

Os criptogramas resultantes de cifrar dois textos-limpos diferentes (P1 e P2) com a mesma chave K e o mesmo NONCE N são dados por:

```
C1 = P1 ⊕ KS
C2 = P2 ⊕ KS
C1 ⊕ C2 = (P1 ⊕ KS) ⊕ (P2 ⊕ KS) = P1 ⊕ P2
```

onde:

* `C1 e C2` são os criptogramas
* `P1 e P2` são as mensagens (*plaintexts*)
* `KS` é o *keystream* gerado pela cifra

Um atacante que obtenha os dois criptogramas pode calcular o XOR das duas mensagens originais, quebrando a cifra. Portanto, reutilizar um NONCE é equivalente a reutilizar uma chave OTP, o que é proibido.

Assim, ao utilizar um **NONCE fixo**, estamos a comprometer a segurança da cifra, pois equivale à reutilização do mesmo *keystream*, o que constitui uma vulnerabilidade semelhante ao problema de reutilização de chave no OTP.


## Questão 2

Para testar o comportamento da cifra ChaCha20, foi criada uma mensagem de teste que foi posteriormente cifrada. De seguida, foi alterado apenas um bit no primeiro byte da mensagem original, e a nova mensagem foi cifrada novamente utilizando a mesma chave e o mesmo NONCE.

Para garantir que o mesmo NONCE é utilizado em ambas as cifragens, foi temporariamente definida a seguinte linha no programa:

```python
nonce = b"\x00" * 16
```

Desta forma, o *keystream* gerado pela cifra permaneceu igual em ambas as operações de cifragem.

Ao comparar os dois criptogramas obtidos, verificou-se que apenas um bit do criptograma foi alterado, exatamente na mesma posição do bit modificado na mensagem original. No caso observado, o byte correspondente mudou de `0x78` para `0x79`, o que corresponde à alteração de apenas um bit dentro desse byte.

Isto acontece porque *ChaCha20* é uma cifra sequencial síncrona, em que a cifragem consiste na operação XOR entre o texto-limpo e um *keystream* gerado pela cifra:

```
C = P ⊕ KS
```

Assim, cada bit do criptograma depende apenas do bit correspondente do texto-limpo e do bit correspondente do *keystream*. Como o *keystream* permanece igual (mesma chave e mesmo NONCE), ao alterar um único bit do texto-limpo é alterado apenas o bit correspondente no criptograma, demonstrando que a cifra não promove difusão.


## Questão 3

Um ataque de *bit flipping* consiste em alterar diretamente bits do criptograma, sem conhecer a chave, de forma a modificar a mensagem original após decifração.

### AES-CBC

No modo **CBC**, cada bloco de texto-limpo é obtido através da operação:

```
P_i = D_k(C_i) ⊕ C_{i-1}
```

Se um bit do criptograma C_i for alterado:

- o bloco de texto correspondente (P_i) ficará completamente corrompido (em média, cerca de 50% dos seus bits serão alterados de forma imprevisível).
- o bit alterado em C_i irá afetar exatamente um bit no bloco de texto-limpo seguinte, **P_{i+1}**, na mesma posição do bit alterado, devido à operação XOR com o bloco anterior.

Assim, alterar um único bit do criptograma em CBC afeta todo um bloco da mensagem original e um bit do bloco seguinte.


### AES-CTR

No modo **CTR**, a cifragem funciona de forma semelhante a uma cifra sequencial:

```
C = P ⊕ KS
```
onde *KS* é o *keystream* gerado a partir da key, do nonce e do contador.

Se um bit do criptograma for alterado, apenas o bit correspondente da mensagem original será alterado após decifração, pois cada bit do criptograma depende apenas do bit correspondente do texto-limpo e do *keystream*. Não ocorre propagação do erro para outros blocos da mensagem.


## Questão 4

O programa `chacha20_int_attck.py` explora o facto de a cifra ChaCha20 não garantir integridade dos dados. Conhecendo um fragmento do texto-limpo numa determinada posição, é possível modificar diretamente o criptograma para que, após decifração, apareça um novo texto pretendido.

Ao aplicar este mesmo princípio aos criptogramas gerados pelos programas `cfich_aes_cbc.py` e `cfich_aes_ctr.py`, observam-se comportamentos distintos.

No caso do **AES-CTR**, o ataque funciona de forma semelhante ao ChaCha20, pois o modo CTR também se baseia na operação XOR entre o texto-limpo e um *keystream*. Assim, alterar um byte do criptograma altera diretamente o byte correspondente da mensagem original após decifração, permitindo modificar o conteúdo de forma controlada.

Já no caso do **AES-CBC**, a alteração de um byte do criptograma provoca a corrupção de todo o bloco correspondente após decifração, além de alterar um bit do bloco seguinte, corrompendo também este. Desta forma, não é possível modificar o texto de forma precisa, pois a alteração introduz erros adicionais na mensagem.


## Questão 5

Sim, ambos são necessários e desempenham funções diferentes e complementares numa implementação segura de *password-based encryption* com *ChaCha20*.

Na versão de *password-based encryption* com *ChaCha20* são utilizados dois valores adicionais: o *salt* e o *NONCE*, cada um com funções distintas.

O *salt* é um valor aleatório usado como entrada para a Key Derivation Function (KDF), como a PBKDF2. A sua função é garantir que, mesmo que dois utilizadores usem a mesma password, a chave criptográfica derivada *(key)* seja diferente para cada um. Isto impede ataques baseados em tabelas pré-computadas, como *rainbow tables*, e aumenta a segurança do processo de derivação da chave. Com um salt único por ficheiro, o atacante é forçado a atacar cada ficheiro individualmente.

O *NONCE*, por sua vez, é utilizado diretamente na cifra ChaCha20 durante o processo de cifragem. A sua função é garantir que, se cifrarmos múltiplas mensagens com a mesma chave derivada, o *keystream* gerado para cada mensagem seja único. Desta forma evita-se a reutilização do mesmo *keystream*, o que comprometeria a segurança da cifra.

Assim, *salt* e *NONCE* têm funções diferentes e complementares:
- O *salt* protege contra ataques à password e garante que a mesma password pode originar chaves derivadas diferentes.
- O *NONCE* protege contra ataques à cifra e garante a unicidade do *keystream*.
Por esta razão, ambos são necessários numa implementação segura de *password-based encryption* com *ChaCha20*.
