## Exercício 1: Reconhecimento de SQL Injection

### Payload 1: `' OR '1'='1`

Output obtido:
```
[DEBUG] Executing SQL: SELECT id, title, body FROM notes WHERE title LIKE '%' OR '1'='1%'
  [1] Welcome: This is your first note.
  [2] Reminder: Submit the SSI lab report on time.
  [3] Secret: The admin password is hunter2.
```

Este payload introduz uma condição lógica adicional na cláusula `WHERE`. Como a expressão `'1'='1'` é sempre verdadeira, então a consulta devolve todos os registos da tabela `notes`, incluindo informação que normalmente não seria apresentada ao utilizador.

### Payload 2: `' UNION SELECT 1, sql, '' FROM sqlite_master --`

Output obtido:
```
[DEBUG] Executing SQL: SELECT id, title, body FROM notes WHERE title LIKE '%' UNION SELECT 1, sql, '' FROM sqlite_master --%'
  [1] CREATE TABLE notes (id INTEGER PRIMARY KEY, title TEXT, body TEXT): 
  [1] Welcome: This is your first note.
  [2] Reminder: Submit the SSI lab report on time.
  [3] Secret: The admin password is hunter2.
```

Este payload utiliza a cláusula `UNION` para combinar os resultados da consulta original com uma nova consulta sobre a tabela especial `sqlite_master`, que contém informação sobre a estrutura da base de dados. Desta forma, o atacante consegue obter o esquema da tabela, incluindo os nomes das colunas e a definição da estrutura de armazenamento.

### Payload 3: `' UNION SELECT 1, title, body FROM notes --`

Output obtido:
```
[DEBUG] Executing SQL: SELECT id, title, body FROM notes WHERE title LIKE '%' UNION SELECT 1, title, body FROM notes --%'
  [1] Reminder: Submit the SSI lab report on time.
  [1] Secret: The admin password is hunter2.
  [1] Welcome: This is your first note.
  [2] Reminder: Submit the SSI lab report on time.
  [3] Secret: The admin password is hunter2.

```

Neste caso, o utilizador utiliza novamente a cláusula `UNION`, de forma a consultar diretamente os dados armazenados na tabela `notes`. O resultado é a apresentação de todas as notas da base de dados, incluindo a nota secreta que contém a palavra-passe administrativa.

---

Esta vulnerabilidade existe porque a consulta SQL é construída através da concatenação direta de strings controladas pelo utilizador:
```python
sql = "SELECT id, title, body FROM notes WHERE title LIKE '%" + query + "%'"
```

Como o input do utilizador é interpretado pelo motor SQL como parte do comando, torna-se possível alterar a lógica da consulta e executar instruções não previstas pelo programador.

## Exercício 2: Command injection

### Caso 1: Utilização normal - `note.txt`

Resultado: A nota foi exportada corretamente para o ficheiro indicado.

### Caso 2: `note.txt; cat /etc/passwd`

Resultado: O caracter `;` permite encadear múltiplos comandos na shell. Assim, depois da exportação da nota, foi executado o comando `cat /etc/passwd`, que exibe o conteúdo de um ficheiro crítico do sistema operativo.

### Caso 3: `note.txt; id; whoami`

Resultado: Após a exportação da nota, foram executados os comandos `id` e `whoami`. Estes comandos revelam informação sobre a conta de utilizador que executa a aplicação, incluindo o UID, grupos e nome de utilizador.

### Caso 4: ``` `ls -la` ```

Resultado: Foi executado o comando `ls -la`.

O output da listagem da diretoria foi incorporado pela shell durante a expansão dos backticks. Posteriormente, a aplicação tentou utilizar o resultado dessa expansão como nome de ficheiro, originando um erro.

---

### Explicação da Vulnerabilidade

A vulnerabilidade encontra-se na construção do comando:
```python
cmd = f"echo 'Title: {row[0]}\nBody: {row[1]}' > {filename}"
os.system(cmd)
```

O valor de `filename` é controlado pelo utilizador e é inserido diretamente numa string que será interpretada pela shell. Caracteres especiais como `;`, `&&`, `|`, `$()` e *backticks* permitem introduzir novos comandos que serão executados com os privilégios da aplicação.

Num servidor real, um atacante poderia:
- Ler ficheiros sensíveis do sistema;
- Obter informação sobre utilizadores e configurações;
- Modificar ou apagar ficheiros;
- Instalar malware;
- Executar comandos arbitrários;
- Obter controlo total da máquina caso a aplicação execute com privilégios elevados.

Concluindo, esta vulnerabilidade é extremamente crítica, pois permite a execução arbitrária de comandos no sistema operativo, o que pode levar a consequências graves para a segurança do servidor e dos dados armazenados.


## Exercício 3: Remediação segura (SQL injection)

Correção de `search_notes`:
```python
def search_notes(query):
    """Search notes by title: SAFE version."""
    conn = sqlite3.connect(DB_FILE)

    sql = "SELECT id, title, body FROM notes WHERE title LIKE ?"

    try:
        cursor = conn.execute(sql, ("%" + query + "%",))
        results = cursor.fetchall()

        if results:
            for row in results:
                print(f"  [{row[0]}] {row[1]}: {row[2]}")
        else:
            print("  No notes found.")

    except sqlite3.Error as e:
        print(f"  SQL error: {e}")

    conn.close()
```

A execução dos payloads do Exercício 1 resulta sempre em "No notes found."

A vulnerabilidade foi eliminada através da utilização de uma query parametrizada. Em vez de concatenar diretamente o input do utilizador na instrução SQL, a consulta utiliza o placeholder `?`, sendo o valor fornecido separadamente através da API do SQLite.

Desta forma, o conteúdo introduzido pelo utilizador é tratado exclusivamente como dados e nunca como código SQL. Mesmo que o utilizador introduza caracteres especiais ou payloads de *SQL injection*, estes serão interpretados como texto literal.

A funcionalidade de pesquisa por padrões continua a funcionar através da utilização dos wildcards `%` adicionados ao parâmetro fornecido à query.

Após a correção, os três payloads utilizados no Exercício 1 deixam de produzir resultados indevidos, demonstrando que a vulnerabilidade foi mitigada com sucesso.

## Exercício 4: Remediação segura (command injection)

Correção de `export_note`:
```python
from pathlib import Path

def export_note(note_id):
    conn = sqlite3.connect(DB_FILE)

    cursor = conn.execute(
        "SELECT title, body FROM notes WHERE id = ?",
        (note_id,)
    )

    row = cursor.fetchone()
    conn.close()

    if row is None:
        print("  Note not found.")
        return

    filename = input("  Enter filename to export to: ").strip()

    if "/" in filename or ".." in filename:
        print("  Invalid filename.")
        return

    with open(Path(filename), "w", encoding="utf-8") as f:
        f.write(f"Title: {row[0]}\n")
        f.write(f"Body: {row[1]}\n")

    print(f"  Note exported to {filename}")
```

A execução com os payloads do Exercício 2 já não provoca a execução de comandos. Alguns payloads são rejeitados pela validação do nome do ficheiro, enquanto outros são simplesmente tratados como nomes de ficheiro normais.

A vulnerabilidade foi eliminada através da remoção da chamada a `os.system()`.

A aplicação já não invoca uma shell para criar o ficheiro. Em vez disso, utiliza diretamente as primitivas de acesso a ficheiros disponibilizadas pelo Python (`open` e `write`). Como não existe qualquer interpretação por parte da shell, caracteres especiais como `;`, `|`, `&&`, `$()` ou *backticks* deixam de possuir qualquer significado especial.

Foi ainda adicionada uma validação simples do nome do ficheiro para impedir tentativas de navegação em diretórios através de sequências como `../`.

Após a correção, todos os payloads utilizados no Exercício 2 passam a ser tratados como texto normal, deixando de ser possível executar comandos arbitrários no sistema operativo.

## Exercício 5: Reflexão

As vulnerabilidades de *buffer overflow*, string de formato, *SQL injection* e *command injection* partilham uma causa comum: a utilização insegura de dados controlados pelo utilizador. Em todos os casos, a aplicação falha ao distinguir claramente entre dados e instruções, permitindo que a entrada externa influencie o comportamento interno do programa de formas não previstas pelo programador.

A validação de entradas é uma medida importante, mas insuficiente quando utilizada isoladamente. É extremamente difícil prever todas as combinações possíveis de caracteres ou formatos maliciosos que um atacante pode utilizar. Um pequeno erro na validação pode permitir a exploração da vulnerabilidade. Por esse motivo, a segurança moderna privilegia mecanismos estruturais que eliminam a possibilidade de interpretação indevida dos dados.

O princípio da parametrização foi aplicado diretamente na correção da *SQL injection* através da utilização de queries parametrizadas. Em vez de construir comandos SQL por concatenação de strings, os dados do utilizador são transmitidos separadamente da instrução SQL. De forma semelhante, a correção da *command injection* eliminou a necessidade de invocar uma shell, utilizando diretamente as APIs de escrita em ficheiros do Python. O princípio do privilégio mínimo complementa estas medidas, limitando os danos caso uma vulnerabilidade seja explorada, através da execução da aplicação com as permissões mínimas necessárias.

Embora os buffer overflows e as vulnerabilidades de string de formato possam ambos expor informação presente na stack, os mecanismos diferem significativamente. Num *buffer overflow*, o atacante sobrescreve regiões adjacentes da memória, podendo alterar variáveis, endereços de retorno e o fluxo de execução do programa. Já numa vulnerabilidade de string de formato, funções como `printf` interpretam especificadores controlados pelo atacante e leem posições da stack que não deveriam ser acessíveis. Assim, o *buffer overflow* baseia-se principalmente na escrita e corrupção de memória, enquanto a vulnerabilidade de string de formato explora a leitura indevida de memória e, em alguns casos, também a escrita através de especificadores específicos como `%n`.
