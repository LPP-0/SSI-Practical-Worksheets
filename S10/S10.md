# Semana 10 - Cross-Site Scripting (XSS)

## Questão 1

**Explain the purpose of Lines ➀ and ➁, why are they are needed?**

As linhas 1 e 2 têm como objetivo obter os parâmetro de segurança anti-CSRF, gerados pelo sistema Elgg:

- `__elgg_ts` (timestamp)
- `__elgg_token` (token de segurança)

O Elgg utiliza estes tokens para garantir que um pedido HTTP que altera o estado da aplicação (como adicionar um amigo) foi realizado intencionalmente por um utilizador autenticado a partir da interface legítima do site, e não por um script malicioso noutro separador ou site.

Estas linhas são necessárias pois quando o worm tenta forjar o pedido de adicionar amigo via JavaScript (AJAX), o servidor Elgg irá rejeitar o pedido se estes tokens não estiverem presentes ou forem inválidos. Como o script XSS está a ser executado no contexto da página da vítima (dentro do domínio do Elgg), ele tem acesso aos objetos JavaScript globais da página (neste caso, o objeto elgg.security.token). O script lê estes tokens legítimos da vítima e anexa-os ao pedido forjado, fazendo com que o servidor acredite que o pedido é legítimo.


## Questão 2

**If the Elgg application only provide the Editor mode for the "About Me" field, i.e., you cannot switch to the Text mode, can you still launch a successful attack?**

Sim, o ataque continuaria a ser perfeitamente viável.

Embora o modo "Editor" tente limpar o input no lado do cliente, convertendo caracteres especiais em entidades HTML, esta medida é meramente cosmética e não elimina a vulnerabilidade de Cross-Site Scripting (XSS). A segurança de uma aplicação nunca deve depender de restrições na interface do utilizador (UI).

Um atacante pode contornar esta limitação através de várias técnicas:

- Interceção e Manipulação de Pedidos: Utilizando ferramentas como o Burp Suite ou as ferramentas de programador do browser, o atacante pode intercetar o pedido POST de atualização do perfil e substituir o texto limpo pelo código JavaScript malicioso real antes de este ser enviado para o servidor.

- Falhas na Limpeza do Servidor: Se o servidor não realizar uma validação e codificação (output encoding) rigorosa dos dados antes de os guardar na base de dados e os exibir a outros utilizadores, o script será executado independentemente do modo como foi introduzido.

- Vectores de Injeção Alternativos: O atacante pode explorar outros campos de entrada, falhas na codificação de saída em diferentes partes da aplicação ou pontos de injeção não protegidos que não utilizem o modo "Editor".

Em suma, restringir o modo de edição é uma medida de conveniência para o utilizador e não uma barreira de segurança eficaz. A mitigação real de ataques XSS exige sempre a validação de dados no lado do servidor e a codificação adequada de todos os dados dinâmicos antes de serem renderizados no browser.

## Questão 3

Este ataque enquadra-se na modalidade de **Stored XSS (XSS Persistente)**.

A principal característica que define este ataque como Stored XSS é o facto de o código malicioso ser armazenado permanentemente no servidor da aplicação, que neste caso, é armazenado na base de dados do Elgg, dentro do campo "About Me" do perfil do Samy.

Diferente das outras modalidades:

- Não é Reflected XSS, porque o script não é enviado através de um link malicioso que é "refletido" imediatamente pelo servidor. Ele reside no servidor e aguarda que qualquer utilizador visite a página.

- Não é puramente DOM-based XSS. Embora a execução ocorra no browser (DOM), a origem do código malicioso vem de uma resposta do servidor que contém o script guardado, e não apenas de uma manipulação de dados locais no cliente (como fragmentos de URL).

Neste cenário, o ataque é particularmente perigoso porque qualquer utilizador que visualize o perfil do Samy será automaticamente afetado, sem necessidade de clicar em links externos suspeitos.

## Questão 4

Os três websites diferem na forma como aplicam Content Security Policy (CSP), o que resulta em diferentes níveis de restrição na execução de JavaScript.

## www.example32a.com

Este site não define qualquer política CSP.

- Todos os scripts são executados com sucesso:
  - Inline scripts com nonce
  - Inline scripts sem nonce
  - Scripts locais (self)
  - Scripts externos (example60.com e example70.com)
  - Evento do botão (onclick)


Sem CSP, o browser não impõe restrições à execução de JavaScript. Todo o código presente na página ou injetado é executado.

---

## www.example32b.com

CSP definida no Apache:

```apache
default-src 'self';
script-src 'self' *.example70.com
```

- Inline scripts bloqueados (Failed)
- Scripts locais (self) permitidos
- Scripts externos de example60.com bloqueados
- Scripts externos de example70.com permitidos
- Botão (onclick inline) não funciona

A política `script-src 'self' *.example70.com` limita a execução de JavaScript a scripts da mesma origem e do domínio `example70.com`.  
Scripts inline são bloqueados por não pertencerem a uma origem confiável definida pela política.

---

## www.example32c.com

CSP definida via PHP com nonce:

```php
script-src 'self' 'nonce-111-111-111' *.example70.com
```

- Inline script com nonce correto executa (area1)
- Inline script com nonce incorreto bloqueado (area2)
- Inline script sem nonce bloqueado (area3)
- Scripts locais (self) funcionam
- Scripts externos de example60.com bloqueados
- Scripts externos de example70.com funcionam
- Botão (onclick inline) não funciona

A política CSP permite a execução de scripts inline apenas quando incluem o nonce correto definido pelo servidor.  
Scripts sem nonce ou com nonce inválido são bloqueados pelo browser.  
Scripts externos continuam sujeitos às restrições de origem definidas na política (`self` e `example70.com`).
